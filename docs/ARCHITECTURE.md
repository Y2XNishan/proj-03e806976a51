# Architecture and analysis rules

The React client calls FastAPI under `/api`. The backend alone reads Elexon during an explicit local refresh and computes the analysis. Runtime requests load the read-only January 2026 bundle supplied with the application, never Elexon or an ephemeral production SQLite database. The ignored `backend/data/elexon.sqlite3` is only a local refresh workspace. The React dashboard fetches the month once, filters interval rows by purchase-decision date, and requests server-calculated `/api/accuracy?decision_date_from=...&decision_date_to=...` for selected ranges. It does not calculate MAE, RMSE, or bias in the browser.

## Durable historical snapshot and startup

Run `python -m app.refresh` from `backend/` to fetch the two streams into SQLite; failed download or source validation leaves the previous complete cache in place. Run `python -m app.snapshot_store` to validate and export the cache to `backend/snapshots/`. The manifest names a SHA-256 content-addressed gzip payload. It records source URLs, retrieval time, decision and delivery periods, and source row counts. The gzip preserves original FUELHH and WINDFOR JSON rows, including forecast publication times and generation values, plus the individual fetched window counts. It is 118,484 bytes, small enough to version as an intentional source-backed deployment asset. Large generated SQLite and frontend output remain ignored.

At load, the backend checks the manifest's schema, filename, checksum, source identity, row counts, all 63 required nonempty source windows, record fields, and analysis integrity. The bundled result is memoized per manifest modification time and cutoff; API requests do not repeatedly decompress it. Missing or corrupt data returns 503, not fabricated or silent fallback output. `SNAPSHOT_REQUIRED=1` enforces that behavior even when the asset is absent. `ELEXON_CACHE_PATH` explicitly selects SQLite for local investigation. A manual refresh and new deployment are required to change production data. The raw asset supports a different configured `DAY_AHEAD_CUTOFF_LOCAL` without changing source values, although any new cutoff still needs decision-methodology review.

## Provenance and verified API behavior

Only two [Elexon BMRS Insights dataset streams](https://developer.data.elexon.co.uk/) are used:

- [FUELHH stream](https://data.elexon.co.uk/bmrs/api/v1/datasets/FUELHH/stream), filtered by `settlementDateFrom`, `settlementDateTo`, and `fuelType=WIND`. The official [OpenAPI schema](https://data.elexon.co.uk/swagger/v1/swagger.json) describes a JSON array with `dataset`, `publishTime`, `startTime`, `settlementDate`, `settlementPeriod`, `fuelType`, and nullable `generation`. The stream reports average MW over each half-hour.
- [WINDFOR stream](https://data.elexon.co.uk/bmrs/api/v1/datasets/WINDFOR/stream), filtered by `publishDateTimeFrom` and `publishDateTimeTo`. Its JSON array contains `dataset`, `publishTime`, `startTime`, and nullable `generation`. The publication-time filters expose historical forecast revisions; omitting them requests the latest publication, which this application never does.

The OpenAPI stream operations expose no pagination parameters. Refresh requests one UTC publication day per WINDFOR call and one settlement date per FUELHH call, rather than a single large month window. The client has 30-second read and 10-second connection timeouts and retries timeouts, network failures, HTTP 429, and HTTP 5xx responses with bounded backoff. Malformed JSON shapes and other HTTP errors stop the refresh. A zero-record daily window is recorded and warned about; the API does not fabricate a substitute.

On 1 November 2026, a real refresh returned 18,688 WINDFOR rows for 31 December 2025–31 January 2026 publication windows and 1,488 FUELHH WIND rows for 2 January–1 February 2026 delivery dates. Each of the 32 forecast windows returned 584 rows in eight distinct publication batches; each of the 31 actual windows returned 48 rows. None of those source `generation` fields was null. The selected delivery forecasts start hourly, so exact matching covers 744 of 1,488 half-hours, with 744 missing forecasts and no missing actuals. On this snapshot the hour-start MAE is 1,883.98 MW, RMSE is 2,350.33 MW, and signed bias is +1,685.27 MW. Even those exact starts compare an hourly forecast target with FUELHH's half-hour average, so these are hour-start comparisons rather than complete half-hour forecast performance. Upstream completeness cannot be guaranteed beyond the returned windows; missing eligible intervals are explicitly counted.

## Decision timing and matching

`DAY_AHEAD_CUTOFF_LOCAL=12:00` assumes a purchase decision at noon in `Europe/London` on each date 1–31 January 2026. The challenge does not give a precise market cutoff, so noon is a configurable analysis assumption, not a confirmed UK trading rule. A 31 January decision targets delivery on 1 February. Every delivery day is generated as consecutive 30-minute UTC intervals between two Europe/London local midnights; this also handles 46- or 50-interval DST days correctly.

For each delivery interval, select the WINDFOR row with the greatest `publishTime` **at or before** that decision's cutoff, requiring the row's `startTime` to exactly match the delivery interval's UTC start. A later revision is never considered, even if it is present in the snapshot. A null value in the latest eligible revision is missing, not replaced by an older revision. Compare with FUELHH WIND at that same UTC `startTime`; for multiple actual revisions, use the latest `publishTime`. Exact duplicate rows collapse; conflicting rows at the same source, start, and publication time cause a data-validation error. Missing and null values are excluded from metrics but retained in the time series and coverage counts.

## Metric definitions and limits

For each valid matched pair, signed error = forecast MW − actual MW. MAE is the mean absolute signed error; RMSE is the square root of the mean squared signed error; bias is the mean signed error. `matched_intervals` counts pairs with both values. Missing actual and missing forecast counts are independently counted over all expected intervals, so an interval missing both contributes to both counts. The API returns `null` metrics if no valid pairs exist. It does not calculate MAPE or another percentage error: near-zero actual generation makes those ratios unstable, and the two feeds may not describe exactly the same wind-farm population. Accordingly, the reported MW differences should not be interpreted as pure forecast skill without investigating the source coverage.

## Production topology and limits

Recommended deployment is two Vercel projects from one repository: repository root for the Python FastAPI function (`app.py`, `requirements.txt`, `vercel.json`) and `frontend/` for the static Vite build. The API function bundles `backend/snapshots/**`; Vercel's read-only runtime is suitable for this fixed historical dataset. The web build sets the public `VITE_API_BASE_URL` to the API origin plus `/api`; the API allows only the exact web origin via `CORS_ORIGINS`. Browser requests contain no credentials. Production defaults allow no cross-origin requests when `VERCEL` is present without an explicit setting. The API adds `nosniff`, no-referrer and frame-denial headers; the web static host has corresponding headers. Frontend environment variables are embedded into public JavaScript, so no secret belongs in a `VITE_` value. A new web domain or preview origin requires a CORS update. Vercel deployment has not yet been performed.

Docker Compose instead builds a non-root backend with the same bundle and an Nginx static frontend that proxies `/api` on the same origin. This needs no data volume or live Elexon request. Docker was unavailable in the current environment and remains unverified. Both deployment routes avoid ongoing database charges for this fixed period; refreshing requires an explicit review and redeployment. Source coverage and the hourly/half-hour mismatch remain the main analytical limits, regardless of host.
